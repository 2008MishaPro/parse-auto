# Архитектурный флоу

## Границы

Одно ядро и подключаемые адаптеры площадок. Сейчас один процесс сбора Node.js/TypeScript, один Avito adapter, несколько поисков. Отдельный необязательный supervisor управляет жизненным циклом этого процесса. Каждый адаптер отдаёт стандартизированные записи; ядро не знает SSR-селекторов, category ID и endpoint площадки.

| Модуль | Ответственность |
| --- | --- |
| src/core/contracts.ts, registry.ts | Контракт и регистрация адаптеров |
| src/core/monitor.ts, scheduler.ts | Поиски, постоянное расписание, отмена/лимиты |
| src/core/search-groups.ts | Постоянные привязки ID к точному запросу, совместимость старых групп |
| src/core/health-state.ts | Состояние источника и формат истории возможных пропусков |
| src/core/crawler.ts | Baseline, быстрый опрос, сверка, догон, охват |
| src/core/store.ts | Состояние, сохранение наблюдений, сравнение и события |
| src/core/details-state.ts | Отдельное состояние попыток карточек и дополнение vehicle в представлении |
| src/integrations/avito/ | request, extract, normalize, adapter |
| src/integrations/registry.ts | Единая регистрация адаптеров для CLI и проверки supervisor |
| src/transport/ | HTTP-helper; браузерный транспорт пока не реализован |
| src/cli.ts | start/status/export и диагностика |
| src/supervisor.ts, supervision/ | Один дочерний CLI, restart/stop/lock, отдельные логи и память |
| tests/, fixtures/ | Регрессии и source simulator |

## Контракт

`SourceAdapter`: id:string; capabilities(); collectPage(query,cursor,signal); getDetails(id,url,signal) опционально. Реестр не ограничивается enum из четырёх площадок. capabilities содержит pagination:string, sort:string[], publishedAt:boolean и details:boolean. Полей описания фильтров и отдельных лимитов нет; текущая логика ядра непосредственно использует details.

`CollectPageResult`: outcome (success/empty/partial/blocked/auth_required/rate_limited/schema_changed/transport_error/timeout), records, nextCursor, endReached, diagnostics, retryAfterSeconds. EndReached требует подтверждённого конца выдачи; nextCursor=null при ошибке не означает конец. Повтор одного cursor/полного набора ID страницы обнаруживается. Формат cursor принадлежит адаптеру. Для оценки количества страниц diagnostics может передать подтверждённую pageCapacity; фактический itemsOnPage последней страницы не подменяется ёмкостью.

`Listing`: source, externalId:string, url, title, priceMinor:integer|null, currency|null, observedAt, publishedAt|null, vehicle с nullable полями, происхождение существенных полей. Дополненное представление может содержать `enrichment:{observedAt,fields}`: отдельное время карточки и список перенесённых vehicle-полей. Исходный observedAt остаётся временем каталога. Цена в минимальных денежных единицах, без кредита/аванса вместо полной цены. Невалидные записи учитываются в diagnostics, не теряются молча.

`Search`: id, source, исходный URL, enabled, intervalSeconds, overlapPages, sweepIntervalSeconds, maxPagesPerSweep, requestTimeoutSeconds, maxCycleSeconds, необязательный maxDetailsPerCycle. Конфигурация принимает maxCycleSeconds как целое число 1–86400, по умолчанию 90 секунд; overlapPages не может превышать maxPagesPerSweep. maxDetailsPerCycle — целое число 0–10, по умолчанию 0: автоматическое обогащение выключено. Идентичные source + точный URL собираются один раз: выбирается кратчайший интервал, максимальные page/time бюджеты, глубина перекрытия и maxDetailsPerCycle включённых aliases. Tracking-параметры удалять только после проверки их назначения. Более широкие диапазоны не объединять автоматически.

## Флоу запуска и опроса

1. Загрузить config и восстановить store. Зарегистрировать адаптер. Создать monitor; атомарно сохранить привязки всех ID конфигурации, включая выключенные, до первого HTTP. Разрешить активные exact-URL группы в их постоянные storageId и запланировать поиски.
2. Новая query проходит baseline доступной выдачи. Старые записи сохраняются с baseline=true, без события «только что опубликовано». Незавершённый baseline виден.
3. В срок scheduler запускает query; adapter строит запрос и извлекает страницу. Scheduler сохраняет source health с fsync внутри занятой FIFO до возврата результата и следующего запроса. Ядро валидирует, сохраняет наблюдения и сравнивает ID/цены.
4. Страницы обходятся по стратегии crawler. Полезная страница сохраняется сразу; missing page не пропускается при продвижении полного checkpoint.
5. После устойчивого commit публикуются eventId + discovered/price_changed/details_changed; при одинаковом состоянии второго события нет. Вывод/будущие подписчики дедуплицируют по eventId.
6. Устойчиво обновить health, lastAttempt, lastSuccess, lastExhaustedScan, покрытие и nextRunAt. При включённом maxDetailsPerCycle выполнить ограниченное обогащение после каталожного checkpoint в оставшемся времени того же цикла; затем сохранить его отдельную диагностику. Завершение цикла возвращает управление scheduler, не завершает процесс.
7. После паузы/сбоя — catch-up с перекрытием; после успешного догона — обычный polling. Если восстановление недоказуемо, gap остаётся видимым.

## Расписание

Watch — основной режим. Начальная настройка intervalSeconds=120; владелец меняет её, фактические ограничения могут увеличить интервал. Это целевое расстояние между началами циклов, не «120 секунд плюс длительность» незаметно. Просроченная задача не порождает очередь параллельных дублей: запустить один догон, измерить overdue.

Одна query имеет один активный обход. На источник — общий бюджет запросов; первоначально одна активная HTTP-операция. Глубокая сверка отдаёт управление между страницами, чтобы не вытеснять быстрые проверки остальных queries. Нагрузка измеряется; повышение конкуренции требует проверки лимитов. Таймаут, cancellable ожидание, backoff и retry-after; без busy loop.

SourceState хранится отдельно от query: failureCount, blockedUntil, lastAttempt, lastSuccess и lastOutcome операции адаптера. Каталог и карточки используют одну FIFO, общий счётчик отказов и blockedUntil. Последовательные отказы разных поисков увеличивают общий счётчик; success/empty устойчиво сбрасывает его и blockedUntil. Отмена пользователем или общим deadline не создаёт новый отказ источника. Состояние сохраняется внутри FIFO перед release/resolve, callbacks и commit результата. Отказ записи блокирует новые запросы всех очередей scheduler, отменяет активных соседей и распространяет исходную ошибку; это не transport_error. Полученный до deadline результат после health fsync всё ещё сохраняется как полезное наблюдение.

После рестарта authoritative source record определяет первый срок запуска и очередь HTTP; устаревший query failureCount не отменяет успешный общий сброс. Старое состояние без sources оценивается один раз по всем сохранённым queryKey источника, включая ID вне конфигурации: максимальные failureCount и nextRunAt ошибочных queries, последние даты. Положительный старый счётчик помечен legacyEstimate=true, поскольку утраченный общий порядок ошибок восстановить невозможно; первый success/empty снимает признак. При queryKey=null источник можно определить только из текущей регистрации под тем же ID. Инициализация сохраняется до HTTP; существующий source record не перезаписывается старой query.

maxCycleSeconds отсчитывается от начала crawl и включает очередь сохранения, callbacks, FIFO источника, ожидание интервала/backoff, запрос/чтение страниц и карточек, штатную проверку доступа Авито. Deadline отменяет ожидание и получение следующего результата. Уже полученные полезные записи сохраняются с fsync без прерывания записи: фактическое завершение цикла может выйти за лимит ради устойчивого commit. Если последняя страница была подтверждена до deadline, последующее завершение её commit не превращает полный успех в time_budget. Обогащение не получает новый бюджет и при исчерпании остатка не откатывает уже подтверждённый результат каталога.

Исчерпание общего времени даёт partial/time_budget, сохраняет непроверенный cursor и требует полного прохода; baseline, lastSuccess и lastExhaustedScan не продвигаются. Это лимит обхода, поэтому failureCount сохраняется и новый backoff источника не назначается. Отдельный requestTimeoutSeconds по-прежнему даёт ошибку страницы timeout с обычным backoff. После time_budget следующий старт назначается по максимуму из start + interval, finish + min(interval, 10 секунд) и сохранённого backoff источника; остальные циклы используют start + interval с учётом backoff. Так короткий лимит 5 секунд при interval 120 секунд сохраняет целевой старт через 120 секунд.

## Охват

- Быстрый опрос читает не меньше overlapPages, если доступный конец не наступил раньше. Coverage.windowIds хранит source + externalId в форме JSON([source, externalId]) из первых overlapPages успешно проверенных страниц последнего завершённого прохода с головы; все когда-либо известные ID не служат опорой окна.
- Если в обязательном окне нет пересечения с предыдущим windowIds и есть следующая страница, poll становится catch_up и продолжает до доступного конца, maxPagesPerSweep или maxCycleSeconds. coverage.windowOverflow сохраняет факт сдвига прежней верхней части; page budget без завершения даёт partial/window_overflow и явный gap. Первый знакомый ID не завершает ни окно, ни догон. Legacy-состояние без окна требует полного прохода с головы.
- Периодическая сверка всей доступной выдачи и повтор границ страниц. EndReached означает обход доступных страниц, не единый неизменный снимок рынка.
- Повтор ID между разными, неидентичными страницами сохраняется как paginationShiftObserved/overlapRecords. Пригодные записи продолжают сохраняться, но такой проход даёт partial/pagination_shift, не продвигает полный checkpoint и требует нового прохода с головы. Полностью повторившийся набор ID страницы остаётся ошибкой repeated_page.
- При отказе, deadline, наблюдаемом сдвиге или восстановленном хвосте прежнее windowIds сохраняется. Хвост не подтверждает полноту и не заменяет окно; только последующий успешный проход с головы обновляет его и lastExhaustedScan. Успешный обычный poll обновляет верхнее окно, сохраняя прежний полный checkpoint.
- Остановка по watermark возможна только при проверенных timestamp/сортировке и перекрытии. Один знакомый ID/несколько старых записей не являются доказательством конца.
- При нестабильной сортировке/лимите — повторная сверка и статус partial/unknown. Если выдача обрезана, проверенные фильтры позволяют разделить запрос на покрывающие сегменты; границы перекрываются, ID дедуплицируются.
- PublishedAt не используется для отбрасывания поздно индексированных записей. Исчезновение с верхней страницы не означает продажу.
- Coverage хранит режим, страницы, причину остановки, lastExhaustedScan, lag и возможные gaps. Объявление, появившееся и удалённое между опросами, может быть недоступно; уменьшение интервала не даёт абсолютной гарантии.

## Хранение и расширения

Сейчас MonitorService и Crawler зависят от конкретного FileStore; отдельного StoragePort нет. Замена хранилища — направление дальнейшей работы с сохранением семантики устойчивых операций. Файловая реализация: checksummed snapshot.json и append-only journal.ndjson с sequence/eventId/checkpoint; fsync до подтверждения и replay при запуске. Старый каталог только с журналом поддерживается. Обрезанный незавершённый хвост определяется и не считается commit. Наблюдения/события/cursor входят в один batch; итоговое состояние query сохраняется следующим устойчивым batch. Повторный replay идемпотентен. Второй процесс с тем же dataDir запрещается эксклюзивной блокировкой, проверенной на целевой ОС; аварийное освобождение также тестируется. Диск full/повреждение committed файла дают явную остановку записи, не успех сбора.

Снимок содержит sequence, все queries, глобальные записи, отдельную membership каждого поиска, последние подтверждённые цены, ключи page replay, постоянные searchBindings, sources, историю gaps, отдельные detailsStates и все события с исходными eventId/sequence. Старое отсутствие новых полей поддерживается; отсутствие detailsStates означает пустую историю карточек, существующие записи/страницы/события сохраняются. Автоматическое сжатие запускается внутри последовательной очереди store после 1000 новых batches или 8 MiB журнала; ручной compact использует ту же очередь и lock. Сжатие не создаёт batch и не меняет sequence. Новый снимок сначала записывается в уникальный temp, fsync/close, rename; только затем таким же способом публикуется новый журнал с checksummed anchor(sequence, snapshotChecksum). Старый append handle закрывается перед заменой журнала и затем открывается новый.

Между публикациями допустим новый снимок со старым полным журналом: старый префикс проверяется, повторно применяются только sequence после снимка. Журнал должен подтверждать минимум sequence снимка. При одновременной замене читатель со старым снимком и более новым anchor перечитывает пару до восьми раз. Повреждения не превращаются в пустое состояние. Windows может временно запретить rename читаемого файла: замена повторяется ограниченно до 20 раз с паузой 10–100 мс; постоянный отказ останавливает запись. После ошибки автоматического сжатия последний batch уже может быть устойчиво сохранён, хотя вызывающий получил ошибку; replay сохраняет его event ровно один раз. Проверки подтверждают crash процесса до/между/после публикаций. Устойчивость metadata rename при внезапной потере питания Windows не доказана.

Если ответ неполный/ошибочный, но содержит полезные записи, scheduler сначала сохраняет общий source health, crawler одним query batch сохраняет error/backoff/gaps, затем page batch — сами записи без продвижения непроверенного cursor. Это сохраняет Retry-After и причины пропусков при crash после page commit; health/query/page не являются одной атомарной записью. Deadline и остановка пользователем не маскируют ошибки сохранения; monitor дожидается завершения активных владельцев записи и распространяет фатальную ошибку.

CoverageGap содержит gapId, канонический searchId, runId, since|null, until, reason и sequence последнего уточнения. gapId=SHA-256(JSON([searchId,runId,reason])); одна причина одного цикла уточняет один период, сохраняя минимальную since и максимальную until. Неизвестная since=null сохраняется; отрицательный период отклоняется. При откате часов crawler использует null. Отдельные причины одного цикла — process_restart, source_limit, pagination_shift, time_budget, window_overflow и другие — сохраняются вместе с query, не заменяют друг друга. Restart записывается до HTTP; распознанные cap/shift/error — до полезной страницы и callbacks, финальный batch продлевает периоды. Успешный опрос не стирает историю; lastGap сохраняет прежний формат основного основания. Legacy lastGap импортируется один раз перед HTTP, утраченные прежние периоды не выдумываются. CLI status показывает sources/gaps; export --gaps отдаёт только историю. Эта история описывает риск пропусков, не подтверждённые потери объявлений.

Данные: состояние queries/baseline, listings/цены/версии, events, run diagnostics/gaps. Нет таблиц пользователей, ИИ и Telegram. Переход на PostgreSQL потребует выделения интерфейса хранилища и переноса нынешних правил атомарности, сравнения, replay и событий.

Для будущих интерфейсов понадобятся методы управления поисками/статусом/выборкой; list/add/update/pause/resume/getStatus/listRecords/listEvents в MonitorService сейчас не реализованы. Доступ осуществляется через CLI/config, REST API и бот отсутствуют. Новый adapter добавляется модулем и регистрацией, если укладывается в нынешний DTO/пагинацию/стратегию; вторая реальная площадка совместимость ещё не доказала. Новые возможности могут потребовать расширения контракта.

## Фактический исполняемый срез 2026-10-11

Реализованы перечисленные модули, TypeScript напрямую на Node.js 24.19+, pnpm 10.23.0; runtime — native fetch, без дополнительных зависимостей. Исторические проверки 2026-10-11: полная серия характеристик 365/365 и последующий точечный срез диагностики 52/52. Автоматическое обогащение проверено релевантными 201/201 тестами; после найденной ошибки проверки optional enrichment повторены только затронутые DTO/обход — 55/55. Финальный typecheck без emit прошёл. После фикса/фичи весь набор автоматически не запускать: правило владельца в AGENTS.md. Точные результаты живых проверок фиксируются в STATE. Основной монитор штатно остановлен владельцем; настройка обогащения его сама не запускает. Билд без явной просьбы владельца запрещён.

Конфигурация применяется при рестарте. QueryState хранит queryKey=JSON([source,точныйURL]); searchBindings сопоставляет каждый ID с неизменными queryKey и storageId. Новый storageId выбирается из первого enabled ID по алфавиту (при всех disabled — первого ID), затем сохраняется даже при отключении/удалении исходного ID или добавлении более раннего. Интервал и бюджеты объединяются только по текущим включённым ID. coverage.aliases описывает включённые ID последнего завершённого обхода; offline status не загружает config. getQuery/updateQuery/commitPage принимают alias и работают с исходной query, page keys и searchId событий; прежние события/eventId не переписываются.

Регистрация планируется целиком до записи и сохраняется одним checksummed search_bindings batch с fsync; повторная регистрация без изменений не увеличивает sequence. Даже ID на паузе или ранее удалённый из config нельзя использовать для другого source/URL. Старый уникальный queryKey принимается с прежним storageId и запомненными coverage.aliases. queryKey=null можно принять только под исходным ID без доказательства прежних фильтров. Несколько старых query одного затронутого ключа дают явный отказ до HTTP: их цены/события автоматически не объединяются. Несвязанные legacy группы остаются доступными; забытые aliases восстановить невозможно. Проверяются исходный self-binding, единственный root ключа, отсутствие alias-query и конфликтов с запомненными legacy aliases; committed query/page после регистрации обязан использовать storageId.

Store использует snapshot + checksummed journal.ndjson с sequence, fsync, page/events/cursor batch и эксклюзивный каталог writer.lock. Replay, truncated-tail recovery, Windows crash/lock, snapshot/compaction, ошибки публикации/reopen и конкурентные читатели проверены. Сжатие устраняет повторные наблюдения в журнале, однако все события/ключи page replay/записи сохраняются: размер снимка и память могут расти, а малый журнал после сжатия может занимать вместе со снимком больше места. CLI stdout не имеет автоматической повторной доставки после crash; устойчивые eventId/события доступны через export.

Рабочая структура общая для всех поисков: searches.json, data/state, data/run, data/exports, data/reports. Регион/бюджет не влияют на папки или код ядра. Read-only FileStore.inspect(dataDir, searchId?) разрешает alias в storageId и выбирает records из сохранённого searchRecords membership с vehicle-дополнением, events/gaps по каноническому searchId. detailsStates содержит отдельные карточные evidence/receipts выбранных identity. Без ID возвращается полный снимок; неизвестный/пустой ID отвергается. Общие queries/bindings/sources сохраняются в диагностике. CLI export --search-id не использует observedAt как признак принадлежности.

Есть baseline, overlap polling с сохранённым верхним окном, расширение catch_up, периодическая доступная сверка и продолжение failed cursor. Общий maxCycleSeconds и наблюдаемый сдвиг между страницами дают явный partial вместо полного успеха. Восстановленный хвост не считается полным сканом. Page budget, повтор cursor/набора ID, неизвестная разметка и source cap также видны в partial/error. baselineNeedsBudgetIncrease, baselineNeedsTimeBudgetIncrease и requiredAction объясняют недостаточный бюджет; overdueMs показывает просрочку, elapsedMs/timeBudgetExhausted — длительность и deadline. lastGap и отдельная история всех сохранённых gaps сохраняются после успешного опроса; source health восстанавливается независимо от query.

Один источник имеет FIFO, одну активную операцию, минимальный интервал страниц 2 сек и backoff 10–300 сек либо больший Retry-After. Backoff/nextRunAt сохраняются до внешнего вывода ошибки. Параметры нагрузки — стартовые; длительная приемлемость не доказана. Слабый адаптер обязан соблюдать AbortSignal: автоматическая изоляция зависшего стороннего кода отдельным процессом не добавлялась.

После рестарта общий source backoff и точный счётчик последовательных отказов восстанавливаются из SourceState. Только прежние данные без source record используют однократную явно отмеченную legacy оценку по query; их точный исторический порядок отказов восстановить нельзя.

Авито: SSR primary items, nullable цены/vehicle/publishedAt; next URL принадлежит адаптеру. Живые страницы 1/2 различаются, p30 подтверждает конец доступных 1500, но исходный поиск около84тысяч. Количество широкого каталога не обещает полного охвата. Три карточки получены с HTTP 200; ID/названия/полные цены совпали с выдачей. Сдвиг и переполнение проверяются управляемым simulator; полнота живой выдачи и пилот 24–48 часов ещё не доказаны.

Текущий региональный URL задаёт Волгоградскую область и цену до 150 000 ₽ средствами Авито; SSR подтвердил locationId=624770 и priceMax=150000. Марка не ограничена, ВАЗ выделяется только в диагностической выгрузке. Короткая последняя страница большого поиска дополнительно подтверждается точным сжатым pager 1/last−1/last/«…»→last−2 и prev=last−1 при сохранении всех проверок счётчиков, остатка и уникальности. pager.start может быть числом и не используется как URL. Живой полный проход 23 страниц завершил baseline; следующий poll обнаружил сдвиг, сохранил полезные страницы и прежний полный checkpoint, установил requiresFullScan.

AvitoAdapter владеет одной AvitoHttpSession с native fetch и приватным cookie jar в памяти. Сессия сохраняет Set-Cookie также при отказе, учитывает domain/path/expiry, сериализует операции и оставляет cookies только на допустимом Avito origin. HTTP-переходы выполняются вручную, максимум три; cookies промежуточного ответа не теряются. Минимум 2 секунды между всеми сетевыми обращениями, включая служебную проверку; общий таймаут охватывает очередь, тело, CPU и повторную загрузку.

Для наблюдавшегося 439 поддержан один штатный цикл `/web/3/firewallPow/get` → ограниченный SHA-256 proof → `/verify` → reload. Произвольный JS не исполняется. Неизвестная проверка, превышение сложности/бюджета, неверный ответ и повторный отказ остаются ошибкой. Retry-After не обходится служебным POST. `httpRequests/accessCheck/accessCheckReason` безопасны для журнала, cookies/JWT туда не входят; фактический HTTP 200 со страницей отказа сохраняется как HTTP 200 + outcome blocked.

Опциональный getDetails отдаёт CollectDetailsResult: outcome, один record или null, diagnostics, retryAfterSeconds. Независимый parser читает JSON `window.__staticRouterHydrationData.loaderData['catalog-or-main-or-item'].buyerItem`; item сверяет ожидаемые ID/category/URL, а цену подтверждает item.price + formattedPrice.value + полная RUB-строка. Ядро может вызывать этот общий контракт для ограниченного vehicle-обогащения. Независимая контрольная сверка остаётся в scripts/check-avito-cards.ts и не меняет store/events/checkpoints.

Автомобильные year/mileageKm каталога выводятся только из наблюдавшихся строгих title-суффиксов `, YYYY, N км` и `, YYYY, битый, N км`, с явным provenance title. Проверяются safe integer, тысячные группы и год 1886…observedAt year+1; неизвестное остаётся null. Make/model из свободного названия не выводятся. Карточка дополнительно читает плоские brand/model/year/mileage в buyerItem.ga: фактический индекс не закреплён, различные полные наборы дают неоднозначность. Подтверждение требует совпадения year/mileage со строгим title, а make+model — с началом title и границей слова. Конфликт сохраняет только title-derived year/mileage; все принятые поля имеют точные пути provenance. Эти служебные SSR атрибуты подтверждены четырьмя живыми карточками, включая иномарку и битую машину, но не гарантированы на каждой. Сырые старые catalog DTO не переписываются; новые каталожные поля появляются при фактическом наблюдении, карточные дополнения хранятся отдельно.

Диагностический scripts/card-verification.ts отдельно отмечает успех getDetails и сравнение двух наблюдений. Проверяются source/ID/title/полная RUB-цена и несогласованность известных year/mileage; неизвестные характеристики не приравниваются к совпадению или различию. Нет полной цены — unverified; несовпадение — mismatch с перечнем полей, а не ошибка транспорта. scripts/check-avito-cards.ts читает persisted source backoff перед каждым запросом без writer и прекращается при будущем blockedUntil или первом source refusal. Read-only отчёт не создаёт события и не меняет source/query checkpoints.

details_changed сравнивает название всегда, а nullable publishedAt/make/model/year/mileage — только если значения известны в обеих соседних записях. Обогащение null→known и потеря known→null сохраняют фактическую запись без ложного события; разницу через промежуток unknown не устанавливаем. Изменение известных каталожных значений по-прежнему создаёт событие. Каталожное сравнение и отдельная история knownPrices, price_changed и discovery не используют карточное представление.

## Ограниченное автоматическое обогащение

При maxDetailsPerCycle больше нуля crawler после успешного устойчивого каталожного checkpoint выбирает кандидатов из всей сохранённой membership данного поиска, включая карточки прежних страниц и циклов. Ограничения первой страницей или 50 ID нет. FileStore.detailsCandidates(searchId, limit, now) сначала возвращает eligible identity без прежней попытки в устойчивом порядке membership, затем eligible ранее попытанные по attemptedAt ASC; равные времена сохраняют порядок membership. Отбор и ограничение числа запросов разделены: рабочий бюджет по-прежнему 2. Прогресс задаётся существующими durable receipts; новый cursor/формат snapshot не нужен. Aliases разрешаются в исходный storageId, другие поиски не смешиваются. Неполный/ошибочный каталог, восстановленный хвост, pagination shift и source cap запрещают карточный этап; поддержка details обязательна.

Карточки идут последовательно через общую с каталогом source FIFO и транспортную сессию, соблюдают исходный deadline/maxCycleSeconds и requestTimeoutSeconds. Новый бюджет после каталога не создаётся. При активном backoff запросы не начинаются; первый карточный отказ прекращает обогащение и сохраняет source health и retryAt. Каталожный checkpoint и его результат от этого не откатываются. coverage.enrichment и diagnostics details_started/details_result/details_finished показывают selection=saved_search, лимит, кандидатов, попытки, результаты, время и stopReason; прежнее scopeRecords первой страницы больше не используется; это диагностика, а не события изменения объявлений.

Перед HTTP store атомарно проверяет membership и общий receipt source+externalId, затем сохраняет pending claim с attemptId, catalogTitle, attemptedAt и retryAt. Cooldown действует между разными поисками и названиями той же identity; при crash или отмене неизвестный исход не повторяется немедленно. После ответа отдельный checksummed batch сохраняет outcome и последнюю успешно разобранную raw карточку. Result с неверной identity/некорректным DTO становится schema_changed до commit. Неуспешный ответ не применяется к vehicle и не стирает прежнее успешное evidence. Receipt и raw record переживают replay/compact/restart; старые состояния без detailsStates поддерживаются.

Сырые records/membership каталога, knownPrices и его события не изменяются карточкой. Представление inspect/export дополняет только null поля make/model/year/mileageKm, если title совпадает точно и нет конфликтов двух известных vehicle значений. При конфликте или несовпадении title сохраняется только evidence, без переноса даже недостающей марки/модели. Принятые поля получают карточный vehicle.* provenance; enrichment.fields перечисляет только дополнения, enrichment.observedAt остаётся временем карточки. Catalog price/currency/title/url/observedAt/publishedAt сохраняются, карточки не создают discovered/price_changed/details_changed.

Успех кэшируется при неизменном catalogTitle, включая ответ без дополнительных характеристик. Если каталог позже совпал с уже полученным card.title, повторный GET также не требуется. Другой новый title может стать кандидатом после общего cooldown. Периодической перепроверки успешных карточек и свежести характеристик по TTL пока нет. Сохранённый backlog участвует в последовательном обходе между циклами. При постоянном притоке новых непрочитанных ID готовые retries могут откладываться; исчезнувшие объявления пока не исключаются автоматически.

Отчёты — data/reports/enrichment-live.json, enrichment-restart.json, enrichment-summary.json. SHA-256 основного snapshot/journal не изменился; рабочий supervisor остаётся stopped/processAlive=false. ## Supervisor

Supervisor использует Node fork/IPC без зависимостей. Он проверяет config и регистрацию источников до запуска, получает отдельный эксклюзивный runDir lock и запускает CLI с тем же config. Новый child создаётся только после close предыдущего. Неожиданный exit, включая code0, вызывает ожидание 5–60 секунд; пять коротких завершений за десять минут дают halted. Длительно работавший child сбрасывает серию быстрых сбоев. Writer lock и сохранённые source backoff/checkpoints не изменяются supervisor.

Остановка через stop-файл текущего runId, сигнал или duration отправляет IPC и ждёт закрытия monitor/store. Через десять секунд разрешён force kill с обязательным ожиданием close; после остановки restart запрещён. CLI устанавливает disconnect listener до async startup и использует маркер контролируемого child для ранней потери IPC. При аварии parent обычный child отменяет обход и закрывает store. После доказанной смерти parent stale lock нельзя восстановить, пока записанный childPID жив или не поддаётся проверке. Авария между fork и публикацией PID остаётся узким окном; writer lock предотвращает двух владельцев данных. CPU-зависший child должен соблюдать отмену: отдельного watchdog для живого процесса нет.

stdout child сохраняется в events.jsonl, stderr — diagnostics.jsonl, lifecycle и выборочная память — supervisor.jsonl. status.json публикуется через temp/fsync/rename. RSS/heap/uptime снимаются примерно раз в десять секунд; максимум относится только к этим замерам. CLI status дополнительно проверяет существование parentPID: оставшийся после аварии status=running сам по себе не подтверждает жизнь процесса. При достижении 256 MiB любого лога supervisor останавливает child и даёт halted/log_limit; файлы не удаляются и перед новым запуском требуют ручного архивирования. Автозапуск после перезагрузки компьютера не настроен.
